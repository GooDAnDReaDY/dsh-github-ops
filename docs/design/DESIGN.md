# DESIGN — dsh-github-ops

Контракт продукта: что плагин обещает пользователю и агенту, как выглядит его
поверхность и по каким границам принимается работа. Внутренний документ: в npm и
GitHub-зеркало не публикуется.

## 1. Задача

Дать агенту операции с GitHub, которых нет в существующем GitHub-плагине и без которых
релизный конвейер делается руками: **релизы, теги, универсальный API, запуски workflow,
секреты и правила, санитизированная публикация зеркала**.

Пользователь — владелец DSH-развёртывания, который выпускает плагины: ему нужен один
инструмент вместо последовательности ручных `gh`-команд, с понятными отказами и без
риска опубликовать в публичный канал лишнее.

## 2. Границы

**Входит:** операции GitHub (REST v3 и GraphQL v4) как инструменты агента, карточка
настроек плагина, санитизированная публикация зеркала.

**Не входит:** хранение токена (это сервис учётных данных DSH), дублирование
инструментов сторонних плагинов ради совместимости, любые операции с чужими
репозиториями без явного указания, автоматическая публикация релизов без решения
владельца.

## 3. Пользовательские сценарии

| # | Сценарий | Как выглядит для владельца |
|---|---|---|
| 1 | Выпустить релиз | Агент создаёт тег, релиз с заметками и помечает его `latest` — владелец видит готовую страницу релиза вместо ручных команд |
| 2 | Проверить состояние релизов | Один вызов: список релизов и тегов, какой релиз считается актуальным |
| 3 | Дотянуться до нестандартного API | `gh_api` на чтение свободно, на запись — только с подтверждением |
| 4 | Опубликовать зеркало | Один инструмент: показывает, что уедет и что останется, публикует только продукт, никогда не переписывает историю зеркала |
| 5 | Настроить плагин | Карточка на странице плагина: имя учётной записи с токеном, репозиторий по умолчанию, база API, таймаут |

## 4. Поверхность UI

**Единственная поверхность — карточка настроек на странице плагина** (списочный слот
`plugins.item`, ключ `@goodandready/dsh-github-ops#dsh-github-ops`), плюс легаси-посадка
`settings.plugin.item` для старых ядер. Свой раздел в корне «Настройки» не заводим: это
заявка на постоянное место в списке у всех пользователей, а у плагина нет собственной
подсистемы с навигацией.

Требования к карточке:

- свёрнута по умолчанию, заголовок — кнопка с `aria-expanded`, шеврон — иконка ядра из
  `@deepseek-ai/dsh-client-ui-primitives` с защищённым `require` и своим SVG-fallback;
- форма показывает **статус снимка настроек**, а не только значение: при
  `unavailable`/`loading` поля не выглядят рабочими;
- сохранение пишет **все** изменённые поля и называет поимённо те, что не записались;
- классы с префиксом `gho-`, цвета — только переменные темы, у `<style>` атрибут
  `data-dsh-plugin="dsh-github-ops"`;
- строки: английский исходный + китайский перевод, русский приходит из
  `dsh-russian-lang`.

## 5. Контракт инструментов

- Имена — `gh_*`, совпадают там, где нужен паритет с привычным набором; параметр
  репозитория — `repository: "owner/repo"` с подстановкой значения по умолчанию.
- Чтение свободно. Любая мутация требует `confirm: true`. Удаление релиза/тега — только
  с `confirm: true`.
- Категорический отказ (не подтверждается, а запрещено): удаление репозитория, перенос
  репозитория, удаление организации.
- Ошибки возвращаются значением: `{ ok: false, error, status?, code?, rateLimit? }`.
  Инструмент не бросает исключение наружу и не «съедает» причину.
- Ответы инструментов нормализованы (`tag`, `sha`, `draft`, `latest` и т. п.), а не
  отдают сырой JSON GitHub.

## 6. Данные и безопасность

- Токен: только сервис учётных данных DSH, в настройках — имя. Токен не попадает в логи,
  сообщения об ошибках и README.
- Никаких абсолютных путей, адресов и имён машин в коде и документации.
- Публикация зеркала: allowlist из `package.json → files` + README/LICENSE/CHANGELOG/
  `cordis.patch.yml`; запрет на запретный путь и на отсутствие обязательного файла; один
  коммит поверх зеркальной ветки, fast-forward, никогда не force.

## 7. Приёмка

| Проверка | Критерий |
|---|---|
| Тесты | `npm test` без сети и без харнесса, зелёный |
| Preflight | `dsh-plugin-preflight` без FAIL |
| Живой прогон | список релизов/тегов на нашем репозитории; создание и удаление тестового релиза; `gh_api` на чтение и отказ на мутацию без подтверждения |
| Пакет | `npm pack --dry-run`: нет файлов > 262144 Б, нет `docs/**`, тестов и служебных файлов; README-трио внутри |
| Развёртывание | exact `.tgz` проверен на изолированном test server, затем тот же кандидат принят на production |
| Интерфейс | карточка на странице плагина: заголовок, пояснение, раскрытие, сохранение, статус снимка; проверено в английской и китайской локали |

## 8. Поверхности UI: волна 4

Раздел описывает поверхности, которые добавляются после подтверждения. Общие правила для
всех: нативные токены и компоненты DSH, классы с префиксом `gho-`, строки только
английский источник + китайский перевод (русский приходит из `dsh-russian-lang`), никаких
абсолютных путей и адресов в подписях.

### 8.1 Статус в карточке плагина (пункт 7)

К существующей форме добавляется блок статуса: **источник доступа** (креденшел /
переменная окружения / наша сессия входа / `gh` CLI), **аккаунт**, **скоупы**,
**остаток лимита** и **состояние кэша**. Данные берутся с хост-маршрута
`/dsh-github-ops/status` (по образцу `dsh-memory-meter`: `kind: 'exact'`, только
loopback/тот же origin, fail-closed). Токен в ответ не попадает никогда.

Состояния: `loading` (идёт запрос), `not configured` (ни один источник не отвечает — с
подсказкой, как войти), `ok` (источник, аккаунт, лимит), `error` (маршрут недоступен —
блок говорит об этом, форма остаётся рабочей).

### 8.2 Ссылки на GitHub из чата (пункт 8)

Клик по ссылке `github.com/...` в переписке открывает соответствующую страницу в браузере
и, когда открыта вкладка Source Control, переключает её на нужный репозиторий. Никаких
собственных оверлеев: используется штатное поведение ядра для ссылок; перехват включается
настройкой и по умолчанию выключен.

### 8.3 Полоса PR над полем ввода (пункт 14)

Когда текущая ветка впереди базовой и есть незапушенные коммиты, над полем ввода
появляется **одна строка**: «ветка → база», число коммитов и кнопки «Создать PR»,
«Ревью», «Смёржить». Кнопка не выполняет запись сама: она передаёт модели инструкцию
вызвать соответствующий инструмент, поэтому подтверждение остаётся за штатным контуром
разъятия. Состояния: скрыта (нет расхождения), видима (есть что предложить), `busy`
(инструкция отправлена), `error` (не удалось прочитать git — строка объясняет причину).

### 8.4 Вкладка Source Control (пункт 24) — сделано

Новая вкладка в `conversation.view` (так же, как вкладка Memory в `dsh-memory-meter`:
`slots.inject('conversation.view')` + `slots.register({ name, id, order, label, locale })`),
`order` после chat и trajectory. Состав: шапка репозитория (имя, ветка, ahead/behind,
кнопка обновления), группы изменений (staged / changes / merge), просмотр диффа
(side-by-side и inline), строка коммита (сообщение, amend, commit / commit & push / sync),
ветки, теги, stash, продолжение/отмена merge и rebase, лог git с редакцией секретов.
Данные — с хост-маршрута, как в 8.1; вкладка читает состояние и не пишет без явного
действия пользователя.

**Запись (вторая фаза, сделано).** Строка коммита: сообщение, `amend`, кнопки Commit,
Commit & push и Sync (при отставании — pull с rebase и autostash, затем push; при опережении —
push ветки). Действия над файлами: stage/unstage, discard — с двухшаговым подтверждением.
Ветки: создать от текущей, переключиться, удалить (подтверждение), push ветки. Stash:
сохранить с сообщением, применить, применить с удалением, удалить (подтверждение).
Незавершённые операции: continue и abort (подтверждение) для merge, rebase, cherry-pick и
revert. Каждое действие — именованная операция: хост собирает argv в `lib/scm-write.js`,
валидирует имена веток, пути, сообщения и ссылки stash и **никогда** не собирает shell-строку.

Состояния: `loading`, `empty` (не git-репозиторий — объяснение, а не пустой экран),
`ok`, `error` (git недоступен), `dirty` (подтверждение при отмене изменений),
`conflict` (кнопки accept current / incoming / both).

### 8.5 Панель GitHub во встроенном сайдбаре и better-sidebar (пункт 25) — сделано

Одна панель, два хоста: сначала регистрация во **встроенном сайдбаре DSH**, при
отсутствии — в **better-sidebar** (тот же приём, что в `dsh-live-canvas`:
`registerBetterSidebar(ctx)` плюс `ctx.inject(['betterSidebar'])`). Состав: дерево
репозитория с ленивой загрузкой файлов и подсветкой строк, вкладки Issues / Pull requests /
Actions, инбокс (три колонки), переключатель репозиториев (видимые аккаунту, поиск
публичных, автодетект из `.git/config` текущего рабочего каталога), кнопка «открыть в
браузере». Токен панель не хранит: она ходит на хост-маршрут.

Состояния: `loading`, `empty` (нет репозитория — подсказка выбрать), `ok`, `error`
(нет доступа или лимит — с указанием, когда сброс), `disabled` (панель свёрнута —
опрос останавливается, чтобы не тратить лимит).

## 9. Визуальное направление и основы

- **Атмосфера:** инструмент инженера, а не витрина. Плотная типографика, спокойные
  поверхности, акцент только на действии и на опасном.
- **Референсы (принципы, не копирование):** вкладка Memory в `dsh-memory-meter` (структура
  вкладки, KPI-строка, таблицы), карточки ядра в `dsh-client-ui-settings` (статусы,
  `aria-expanded`, поведение недоступного сервиса настроек).
- **Не копировать:** айдентику, тексты, ассеты и раскладку сторонних плагинов; собственный
  CSS-фреймворк вместо токенов DSH.
- **Цвета:** только переменные темы (`--dsw-*`); цвет не единственный носитель смысла —
  у статусов есть подписи.
- **Типографика:** размеры ядра; моноширинный — для sha, путей и диффов.
- **Сетка:** отступы 8/12/16; узкие экраны — дерево уезжает в выдвижной ящик.
- **Accessibility:** фокус виден, у кнопок есть подписи, у переключателей — `aria-expanded`,
  подтверждения — диалог, а не `window.confirm`.

## 10. Do / Don't

**Do:** показывать, откуда взялся доступ и сколько лимита осталось; предупреждать о
последствиях удаления рядом с действием; останавливать опрос, когда панель не видна.

**Don't:** хранить токен в клиенте или отдавать его в ответе маршрута; выполнять запись из
клиента в обход инструментов; рисовать собственный сайдбар там, где есть нативный.

## 11. Locked Design Decisions

- 2026-09-21 — статус доступа показывается в карточке плагина и на хост-маршруте, но не в
  tool-результате: значение токена не должно попадать в контекст модели. Пересмотр — если
  ядро даст отдельную поверхность для состояния плагина.
- 2026-09-21 — полоса PR над полем ввода только формирует инструкцию, но не пишет: единый
  контур подтверждений остаётся у хоста. Пересмотр — при явном требовании владельца.
- 2026-09-21 — панель GitHub регистрируется во встроенном сайдбаре, better-sidebar —
  фолбэк. Пересмотр — если встроенный сайдбар перестанет давать точку расширения.
- 2026-09-21 — вкладка Source Control повторяет структуру вкладки Memory (слот
  `conversation.view`), а не заводит собственную навигацию. Пересмотр — по требованию
  владельца.
